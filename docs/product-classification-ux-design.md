# P04 入力と次の作業の簡略化

作成日: 2026-10-25。調査対象日: 2026-10-24。既存P04のUI改善に限定する設計契約。
参照実装: `ClassificationPanel.tsx`、`classification-model.ts`、`classification-api.ts`、`server/classification-issues.ts`。
基礎仕様: [P04設計](product-classification-design.md)。本書は入力・表示・移動の仕様を補足し、保存形式と法的判定範囲を変更しない。

## 1. 今回の決定

- 通常の回答状態ドロップダウンを廃止し、実値を直接入力する。未回答はプレースホルダー、意図的な保留は「後で確認する」。
- 親が「なし」の従属欄は省略する。旧回答を保持し、矛盾がある場合だけ展開して修正を求める。
- 新規の金額は税込入力と明記できる。旧金額の税区分は明示変更するまで維持する。
- 保存成功後に次の段階または確認事項へ移動する。保存後は次の未回答・未確認項目を1件提示し、その入力欄へ移動できるようにする。
- 金額からの許可免除、自動業種認定、審査結果、新しい法的状態、P05の契約画面は実装しない。
- `schemaVersion: 1`、全キー、既存Answerの4状態、API、版、監査履歴、サーバーの課題導出を維持する。DB移行とルール版更新は不要。

担当境界: 親担当は `ProductApp.tsx` の静的な次作業帯と基本情報への復帰を実装。sol担当は分類画面・入力・表示用ヘルパー・関連試験を実装。本設計担当の変更ファイルは本書だけ。

## 2. 画面の接続

| 場所 | 表示・動作 |
| --- | --- |
| 工事登録後・通常の工事詳細 | 既定は基本情報。既存タブ順は基本情報、契約前の確認、変更履歴。新メニューを作らない |
| 基本情報の次作業帯 | 「次の作業 / 契約前の確認」。主操作「契約前の確認へ進む」。分類の追加GET・件数・未保存などの推定表示は行わない |
| viewerの次作業帯 | 「保存した確認事項を見る」。分類未保存なら分類画面で「保存した回答はありません」と表示する |
| 分類の段階 | 工事条件、施工範囲、金額と許可、関連条件の既存4段階を維持 |
| 分類から戻る | 任意prop `onBackToJob?: () => void`。表示ラベル「基本情報に戻る」。親の既存 `canLeave` を通してinfoタブへ戻る。callbackなしならボタンを出さない |

基本情報帯は分類の進捗を二重管理しない。分類画面が進捗の表示元になる。説明用の新画面やチュートリアルは追加しない。

## 3. 回答を直接入力する契約

| 保存状態 | 通常の入力UI | 表示・保存上の意味 |
| --- | --- | --- |
| `unanswered` | 選択欄はdisabledな「選択してください」。金額・理由・検索欄は空欄を直接表示 | 選択肢として「未回答」「未入力」を並べない。表示・フォーカスだけでは変更しない |
| `known` | 実値を表示して直接編集 | 初期値を設定するためだけの「内容を入力」は不要 |
| `unknown` | 状態は「未確認」、操作は「入力する」。選択欄では「後で確認する」を選択状態として表現してもよい | 新規に「後で確認する」を押すと既存のunknownを保存。旧unknownを自動変換しない |
| `not_applicable` | 旧回答の「対象外」と理由を表示・必要時編集 | 許された従属欄だけ。通常UIから新規作成させる必要はない |

実装規則:

1. 選択欄には実値と「後で確認する」を置く。金額・候補業種・理由欄は直接入力と補助操作「後で確認する」を置き、別の回答状態selectを重ねない。
2. unknownの理由は追加必須にしない。unknownから「入力する」を押しただけではknownの空値を保存せず、値の入力・候補選択でknownにする。
3. 既知の値をunknownへ変更すると既存union上はvalueがnullになる。金額・候補・理由を取り消すことが分かる明示操作にする。親変更や折りたたみからこの処理を呼ばない。
4. 非空の回答には小さな「回答を取り消す」操作を設けられる。これだけが明示的にunansweredへ戻す経路。プレースホルダーは取消し操作の代用にしない。
5. 候補検索への入力だけではknownにしない。候補追加時にknown、最後の候補を明示的に削除した場合はunansweredへ戻す。既知の空配列を正常保存しない。
6. 理由・施工内容の編集中の空文字、不正金額などは入力エラーを保持し、勝手にunknownに置換して保存を通さない。途中保存でも既存の値検証は守る。
7. 履歴・比較でunknownを「後で確認するを選択済み」と説明しない。旧データにはその操作履歴がないため「未確認（旧表示: 分からない）」または「未確認」で表す。

工事基本情報の施工内容を分類へ流用する場合は「工事の施工内容を使う」という明示操作で説明文をコピーする。既存の説明を自動上書きしない。文章から業種、主従関係、電気工事等の回答を推定保存しない。workItemの安定IDは維持する。

## 4. 金額と税区分

| 場合 | 必須動作 |
| --- | --- |
| 新規のunanswered、まだ数値を入力していない | 例: 「請負額（税込）」と空欄を表示してよい。保存状態はunansweredのまま |
| 上記欄への実際の数値入力 | 明示された税込欄への入力としてknownと `tax_included` を設定できる。0も実値 |
| 旧known / `tax_excluded` | 「請負額（税抜）」と元の数値を表示。数字だけの訂正では税抜を維持 |
| 旧known / `unknown` | 「請負額（税区分未確認）」と元の数値を表示。数字だけの訂正ではunknownを維持 |
| 税区分の明示変更 | 「税込 / 税抜 / 未確認」の既存3値を選択可能。変更しても金額を自動換算しない |
| 既存金額の数字を消す | 元の税区分を保持した編集中の空欄として扱う。保存前に入力修正または回答全体の明示取消しが必要 |
| 未知の金額そのもの | 「後で確認する」でAnswerをunknownにできる。税区分未確認とは別の情報 |

新規の税込表現は、回答値を初期表示時に生成する理由にならない。旧税区分を新規用の税込既定値で上書きしない。特に再マウント、段階移動、現在値の取得、保存成功応答、履歴表示を変換の契機にしない。

税区分だけ先に操作できる実装では、選んだ区分を画面上で保持し、後の数値入力に引き継ぐ。金額が未入力であることを隠さず、正当な既知金額として保存しない。入力途中の一時状態を新しいAPI属性にしない。

金額欄の「未確認」は必要である。税込・税抜のどちらも確認できていない旧値や途中回答を事実どおり保存するためであり、自動的に税込へ寄せて項目を減らすことはできない。

## 5. 親回答と子項目の分岐

対象は既存3組: `suppliedMaterials` -> `suppliedMaterialValue` / `suppliedMaterialTransport`、`splitContracts` -> `relatedContractValue` / `splitReason`、`subcontracting` -> `subcontractTotal`。

| 親 / 子 | 編集画面 | 保存と次項目の扱い |
| --- | --- | --- |
| 親no / 子unanswered | 子の入力欄を出さない | 状態を保持。子を入力待ちに数えない |
| 親no / 子unknownまたは正当なnot_applicable | 「保持している回答」から値・対象外理由を展開可能 | 状態・理由をそのまま送る。子を入力待ちに数えない |
| 親no / 子known | 子を強制展開し、親との矛盾を表示 | 保存不可。親の訂正または子の明示取消し・未確認への変更を求める |
| 親yes / 子unanswered・unknown・known | 子を表示 | 未回答・未確認は次項目の対象。値があれば保持 |
| 親unanswered・unknown / 子unanswered・unknown・known | 親を先に表示。子は補足領域へ折りたたみ可 | サーバーと同様に子も未解決の対象。CTAから展開可能 |
| 親がno以外 / 旧not_applicable | 子と理由を強制展開 | 保存不可。旧理由を残して修正を促す。自動破棄しない |

親変更は親だけを変更する。子の値を0、unknown、unanswered、not_applicableのいずれにも自動変換しない。親をnoからyesへ戻せば、保持した回答が再表示される。

通常の親noで「対象外の理由」を新たに要求しない。サーバーは親noと子unansweredを既に受理する。表示省略と `not_applicable` の保存は別である。

許可欄も同じ原則にする:

- `permit.declaration` は常に入力可能。「保有している（申告） / 保有していない（申告） / 更新手続中（申告） / 後で確認する」。法的な必要性の回答と混同しない。
- `held` / `renewal_pending` では対象工事候補を表示。unanswered / unknownでは「許可の詳細」を折りたたみ可能だが、未解決の入力要求は残す。
- `not_held` とreportedTradesのunansweredは候補欄を省略。unknownは保持して参照可能。knownは矛盾として強制展開し、保存を止める。
- `permit.note` は任意の補足。折りたたんでも内容を保持し、既存の補足があることを示す。
- 表示省略を「許可不要」「免除」「確認済み」と呼ばない。金額を省略条件に使わず、`PERMIT_REVIEW` と金額集計の確認課題を残す。

## 6. 次項目の表示用ヘルパー

以下はsol担当が新設する `classification-flow.ts` の契約。既存APIであるとは扱わない。React・通信・保存に依存しない純粋関数にし、入力オブジェクトを変更しない。

```ts
export type ClassificationTarget = {
  step: 0 | 1 | 2 | 3;
  field: string;
  workItemId?: string;
};
export type ClassificationFlow = {
  nextUnanswered: ClassificationTarget | null;
  nextDeferred: ClassificationTarget | null;
  unansweredCount: number;
  deferredCount: number;
};
export function deriveClassificationFlow(data: ClassificationData): ClassificationFlow;
export function classificationIssueTarget(
  issue: Issue,
  savedData: ClassificationData,
  draftData: ClassificationData,
): ClassificationTarget | null;
```

`ClassificationData` / `Issue` は既存共有型をimportする。型署名は表示仕様であり、新しい保存状態やAPIレスポンスではない。

| step | fieldの固定規則と順序 |
| --- | --- |
| 0 | `context.market`、`context.companyRole`、`context.workKind`、`context.targetKind` |
| 1 | 施工範囲なしは `workItems`。各範囲は `workItem.tradeCandidates`、`workItem.relationship` の順。`workItemId` 必須 |
| 2 | `amounts.contract`、`amounts.suppliedMaterials`、その子2件、`amounts.splitContracts`、その子2件、`amounts.subcontracting`、その子1件、`permit.declaration`、`permit.reportedTrades` |
| 3 | `conditions.electricalWork`、`conditions.existingStructureWork`、`conditions.demolitionWork`、`conditions.specifiedMaterials`、`conditions.constructionWaste`、`conditions.structuralChange` |

各既知金額の税区分がunknownなら `amounts.{key}.taxBasis` を未確認候補にする。任意noteは候補にしない。施工範囲は配列の表示順だがtargetはIDを持つ。実装で追加するdescriptionや附帯先の入力エラー用targetも同じID方式にする。

導出手順:

1. 上表の順で候補を列挙する。親known/noの子、許可known/not_heldのreportedTradesは除く。他は折りたたみ状態と無関係に列挙する。
2. unansweredを未回答列、unknownと既知金額の税区分unknownを未確認列へ入れる。workItems空は未回答1件と数える。
3. 各列の先頭と件数を返す。主CTAは `nextUnanswered ?? nextDeferred`。この件数は入力項目数であり、法的課題件数や達成率ではない。
4. 不正なknown金額、空の施工説明、親子矛盾などは既存 `inputErrors` / `validClassificationData` を先に処理する。入力候補0件を保存可能の判定にしない。

保存済みissueからの移動は `FIELD_UNANSWERED` / `FIELD_UNKNOWN` / `SCOPE_REQUIRED` と既知のpathだけを扱う。`/amounts/contract/value/taxBasis` は `amounts.contract.taxBasis` に対応させる。文字列を無条件にDOMセレクタとして使わない。

`/workItems/{index}/...` は必ずそのissueが属するsavedDataのindexからIDを取り、draftDataで同じIDを探す。削除済み・不正index・未知code/pathならnull。別の施工範囲を誤って開かず、課題の本文は残す。dirtyで対象回答が既に変わった場合は古いissueから編集CTAを出さず、現在の入力案内を使う。

移動操作は対象段階と必要な折りたたみを開き、実入力欄または施工範囲追加ボタンへフォーカスする。移動だけでは値を作らない。ラベルは固定の項目名から作り、例は「次に入力: 支給材料の有無」「入力する」、未確認なら「未確認: 請負額の税区分」「確認して入力」。

## 7. 保存後の進行と課題の表示

主操作は1〜3段階目を「保存して次へ」、4段階目を「保存して確認事項へ」にする。既存の「途中まで保存」を補助操作として残せる。前後の閲覧移動と保存を区別する。

保存処理は既存の検証・権限制御を通し、成功応答のrecord/data/version/basisを採用した後だけ進む。前半は次の段階、最終は同じ画面内の確認事項へ移動し見出しへフォーカスする。保存失敗・競合・結果不明では進行も成功表示もしない。フォーム全項目が埋まることは途中保存の条件ではない。

確認事項の構成は次の3つに限定する。

| 領域 | 内容 |
| --- | --- |
| 先頭の状態 | 保存成功時の「入力内容を保存しました」。競合、前提更新、カタログ不一致は既存の比較・再確認を最優先で表示。対象範囲外の注意も折りたたみに埋めない |
| 次に入力する項目 | flowから1件と移動CTA。他の未回答・未確認は件数付きで展開可能。同じ項目を同じ一覧に重複表示しない |
| 資料で確認が必要な事項 | サーバーのreview、out_of_scope、その他未対応の課題を保持。最初の課題と残件の展開で表示する。既存の根拠リンクを維持 |

保存済みissuesは最後に正常取得したサーバー応答を正本にする。dirty時は「入力中・未保存」の入力案内と「保存済み回答に基づく確認事項」を区別し、下書きだけで法的課題を解消しない。対応できない新しいissueは捨てずに本文表示へ戻す。入力課題を別領域に整理しても、どの課題も参照不能にしない。

入力待ちがなくなっても「回答を保存しました。資料の確認が残っています」と表示する。資料確認群には「資料の審査・契約手続きの画面は現在未提供です」と明記する。これは現状の製品境界であり、契約作成CTA、審査依頼CTA、承認済み表示、完了率を追加しない。使用可能な戻り先は基本情報と既存画面だけ。

## 8. 変更・競合・閲覧権限

- dirtyは値変更、明示取消し、前提の選び直し、未解決の保存照合で維持する。表示省略、折りたたみ、段階、業種の検索語だけではdirtyにしない。
- 保存中は入力・重複保存・保存して進む操作を停止し、離脱も保護する。現行分類画面のdirty式はbusyを含まないため、未変更データの再保存中も親の離脱確認をすり抜けないことを確認する。
- 409・通信結果不明ではloaded / sent / draft / 最新取得結果を保持して比較する。一致だけで直前の保存成功と断定せず、自動再送・自動前提更新をしない。
- staleとカタログ不一致を次項目CTAより優先する。前提選び直し後の保存成功まで、旧前提の課題を解消済みに見せない。
- `onBackToJob` は親の既存離脱確認を使い、二重の確認を追加しない。会社・工事切替、ログアウト、タブから離れる場合も既存の保護を維持する。
- AbortControllerと会社/工事スコープを維持し、遅い応答で別スコープの値・進行・フォーカスを更新しない。ブラウザ永続ストレージへ下書きを追加しない。
- viewerには保存済み値と課題だけを表示する。編集用の次項目CTA、保存、回答取消し、分類履歴を出さない。分類未保存時にも入力を促さない。
- 履歴・比較の `AnswerSummary` は全項目を参照可能にする。編集欄の省略ロジックを流用して旧unknown、税抜、対象外理由を隠さない。現行課題を過去版の判定結果に見せない。

## 9. 許可自動判定を今回追加しない根拠

共有済みの国土交通省[建設業法の基本事項等Q&A](https://www.mlit.go.jp/totikensangyo/const/content/001985869.pdf)を本文で確認した。資料の日付は2026-03-09、参照箇所は2ページQ1と3ページQ3。本書の調査対象日は2026-10-24であり、資料日付を2026-10改訂と表現しない。

同資料は、建築一式以外の軽微工事を500万円「未満」と説明し、消費税等、分割契約の合計、注文者提供材料、単価契約の工事全体額に注意を求めている。建築一式には1,500万円未満または延べ面積150平方メートル未満の木造住宅工事という別の扱いがある。

したがって「500万円以下なら許可業種を省略」は採用しない。500万円ちょうどは500万円未満ではなく、画面の請負額だけでも基準額を確定できない。建築物という回答や建築一式の候補だけで例外を確定しない。

現行モデルには面積・住宅条件などの構造化情報がなく、工事単位・業種・支給材料と分割契約の適切な集計も確認されていない。これは入力項目の数を増やす提案ではなく、自動判定を見送る理由である。今回の安全な派生動作は親回答による表示省略まで。全体の法令網羅性・個別工事の許可要否・資料日付以後の改正全件の照合を完了したとは扱わない。

## 10. 受入ケース

以下はsol・親担当の検証対象。本書だけで実装試験の合格を宣言しない。

| ID | 操作・入力 | 必須結果 |
| --- | --- | --- |
| U01 | 初期表示、フォーカス、4段階の往復、折りたたみ | 全Answerの状態不変。unansweredを選択肢に戻せない。表示操作だけでdirtyにならない |
| U02 | 値の直接入力と「後で確認する」 | 既存known/unknownとして保存できる。空のknownを自動保存しない。旧unknownは保持 |
| U03 | 旧税込・税抜・税未確認の3件を開き、別項目だけ保存 | 各金額・税区分が不変。履歴・比較でも元区分が読める |
| U04 | 新規の税込欄へ0、5000000を入力。旧税未確認の数字だけ変更 | 新規は明示入力後だけ税込。旧値はunknownを維持。税額換算なし |
| U05 | 既存金額の数字を消す、または不正文字を入力して保存 | 元の税区分を維持し入力エラー。0/unknown/unansweredへ黙って置換しない |
